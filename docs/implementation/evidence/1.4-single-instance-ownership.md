## Behavior proven locally

- A stable user-scoped global mutex is created/opened with the minimum required rights, and existing handles are validated against the exact protected SID DACL.
- Existing mutex handles are actually waited on with bounded handling for `WAIT_OBJECT_0`, `WAIT_ABANDONED`, `WAIT_TIMEOUT`, and `WAIT_FAILED`; an abandoned or released owner can be recovered only after fixed-root/state/owner identity checks.
- The fixed `LocalAppData\JARVIS` tree contains the required `data`, `backups`, `logs`, `cache`, `artifacts`, `modules`, `updates`, and `recovery` directories.
- Owner state is a fixed-size checksummed dual-slot record with generation fencing and rejection of impossible idle/pending/acknowledged combinations, including zero request sessions.
- State clients validate regular-file type, no reparse point, exact fixed final path, exact protected ACL, and matching parent/root/SID identity.
- Normal and maintenance roles produce explicit held-role outcomes and never silently treat a role mismatch as a successful second launch.
- Same-session activation requires readiness, exact generation, exact request identity, callback success, acknowledged status, and a bounded acknowledgement event before returning success.
- Open, signal, timeout, acknowledgement, callback false/panic, worker failure, and cleanup failures do not treat an unresolved PENDING/UNCERTAIN request as success; cleanup is generation-fenced, stale queued UI is discarded, and uncertain outcomes fail closed.
- Tauri window show/focus is dispatched through the main UI thread and is bounded; an unacknowledged second launch remains a non-success host result.
- The owner’s activation worker establishes readiness only after a successful bounded wait-loop initialization; a worker failure clears readiness and in-flight requests, and a restarted worker can restore readiness.

## Atomicity, idempotency, failure, and recovery model

The stable mutex is the cross-process arbitration boundary. The fixed state file uses a bounded exclusive lock and dual-slot checksum/commit protocol; each state transition validates the prior generation and commits the next generation before releasing the lock. Activation requests are generation-fenced and cleanup is conditional on the exact request generation, so a stale timeout cannot clear a newer request. External atomicity is not claimed across Tauri and the native owner; the bounded acknowledgement protocol returns success only after the owner has committed the acknowledged state and signaled the event. Ambiguous signal/wait/cleanup outcomes remain typed failures and are not blindly retried as success.
