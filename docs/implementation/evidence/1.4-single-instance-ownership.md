## Behavior proven by the candidate

- One stable user-scoped global mutex is acquired with bounded handling for acquired, abandoned, timeout, and failure outcomes.
- Existing-owner handling validates fixed-root, object/path, owner-state, protected-SID ACL, and handle identity conditions before recovery or activation.
- The fixed `LocalAppData\JARVIS` layout contains `data`, `backups`, `logs`, `cache`, `artifacts`, `modules`, `updates`, and `recovery`.
- Owner state uses a bounded, checksummed dual-slot record with generation fencing and impossible-state rejection.
- Same-session activation is bounded and succeeds only after readiness, exact generation/request identity, callback success, acknowledged state, and acknowledgement signalling are proven.
- Normal and maintenance roles arbitrate explicitly; role mismatch, stale/corrupt state, reparse/UNC/alternate-root conditions, and changed identities fail closed.
- Close-before-release ordering, partial resource closure, repeated lifecycle calls, concurrent lifecycle operations, worker panic/failure, cancellation/release races, and recovery/restart paths are covered by the qualification suite.
- Tauri show/focus dispatch remains bounded and native; an unacknowledged second launch is a non-success result.
- Diagnostics and evidence are bounded, redacted, candidate-bound, and separately hash-bound to retained qualification logs.

These claims describe the tested Section 1.4 scope only. They do not claim completion of the later Core/runtime packaging, IPC, Job Object, provider, persistence, Mission Control, installer, signing, or release sections.

## Atomicity, idempotency, failure, recovery, security, and platform claims

- **Atomicity:** The stable mutex is the cross-process arbitration boundary. The fixed state file uses an exclusive lock and dual-slot checksum/commit protocol; state transitions validate the prior generation and commit the next generation before releasing the lock. Cross-system atomicity between Tauri and the native owner is not claimed.
- **Idempotency/retry safety:** Repeated lifecycle calls preserve the first typed uncertainty until recovery succeeds, then become idempotent success. Activation cleanup is generation-fenced, stale requests cannot clear newer requests, and ambiguous signal/wait/cleanup outcomes are not blindly retried as success.
- **Failure/recovery:** Owner crash, abandoned/released mutex recovery, activation timeout/failure, callback failure/panic, worker failure/panic and restart, state/activation/ack close failure, partial closure, cancellation/release races, stale state, and role contention are covered by the native qualification evidence. Recovery does not report readiness or success before the required owner/resource conditions are restored.
- **Security/least privilege:** Fixed application paths, handle-to-path identity, reparse/UNC/alternate-root rejection, protected-SID ACL validation, object-specific masks, bounded native parsing, no raw handle/path disclosure, and fail-closed unsupported-target behavior are in scope. Job Objects, credentials, IPC, and other later security boundaries are not claimed here.
- **Observability:** Candidate SHA/tree/ref/remote, authority/run/job identity, runner/toolchain, terminal status, bounded diagnostics, evidence JSON hashes, retained-log hashes, artifact IDs/digests, and verifier results are recorded. Raw credentials and unbounded logs are not recorded.
- **Platform:** The qualified runtime is Windows x64 on the stated GitHub runner. The semantic platform boundary remains explicit; Linux, Windows ARM64, and later native capability/release support are not promoted by this subsection.
