The ten contract examples from Platform Portability §26 are preserved exactly. `paths_and_identity`, `privilege_mediation`, and `system_info` are direct semantic identities for the remaining named responsibility interfaces from §6/CS §4; they do not create new product support claims.

Availability and qualification are modeled separately while invalid combinations are made unrepresentable:

- unavailable → necessarily unqualified;
- available + unqualified → technical capability exists but backend use is not qualified;
- available + qualified → technically ready only.

`AVAILABLE + QUALIFIED` is explicitly documented and implemented as **not** user authority, action permission, product support, or release qualification.

## Stable platform errors and fail/degrade path

The exact current stable reason-code foundation is:

```text
PLATFORM_CAPABILITY_UNAVAILABLE
PLATFORM_BACKEND_UNQUALIFIED
PLATFORM_SECURE_STORAGE_FAILED
PLATFORM_IPC_SECURITY_FAILED
PLATFORM_PROCESS_CONTAINMENT_FAILED
PLATFORM_SESSION_OBSERVER_FAILED
PLATFORM_UPDATE_FAILED
```

`checkPlatformCapability` deterministically converts technical discovery to a stable readiness fact:

- unavailable → `ready: false` + `PLATFORM_CAPABILITY_UNAVAILABLE`;
- available but unqualified → `ready: false` + `PLATFORM_BACKEND_UNQUALIFIED`;
- available and qualified → `ready: true` technical fact only.

Whether a dependent feature blocks entirely or degrades is intentionally left to that owning feature's contract semantics. The foundation does not invent a generic fallback and does not convert capability readiness into permission.

Platform adapters may retain sanitized native diagnostics internally, but cross-boundary feature/UI decisions use the stable reason code and semantic capability rather than native human-readable error text.

## Failure / recovery behavior

- Missing capability fails closed as unavailable.
- Present but unqualified backend fails closed as unqualified.
- No generic weak fallback exists.
- Stable failure codes prevent UI/feature code from depending on native human-readable error text.
- No runtime mutation exists to partially apply or recover in this subsection.

## Security / least privilege

- Technical readiness never grants authority or permission.
- Capability IDs cannot encode arbitrary authority-like values.
- Shared contracts contain no native implementation APIs or handles.
- No secret, credential, platform handle, elevated operation, provider authority, or support promotion is introduced.
- Future Linux/Android modeling is not converted into V1 support.

## Observability / diagnostics

Stable reason codes and semantic capability identities provide deterministic machine-readable diagnostics. Sanitized native details may be retained by owning platform adapters later, but they are not part of security/authority branching at this shared boundary.
