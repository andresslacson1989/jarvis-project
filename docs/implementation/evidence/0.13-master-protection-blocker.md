1. implementation work on temporary implementation branches;
2. exact `static-ci` success for the exact candidate before authoritative integration;
3. immediate live-`master` tip revalidation before integration;

5. non-force integration/ref movement only;
6. post-integration reread of the authoritative tip and relevant CI/audit evidence;

## Integration failure/recovery audit

During preparation of the governance-checker fix, two connector-routing mistakes created temporary empty placeholder paths (`__invalid__` and `__invalid2__`) on the implementation branch. They were **not** hidden with force-push/history rewrite. Each was removed with an ordinary follow-up commit. GitHub comparison from the pre-incident tip `ffbcc806...` through the cleanup tip `8d3a5988...` showed **zero files changed**, proving no placeholder path remained in the candidate tree.

The audit history is intentionally preserved. The incident therefore demonstrates the compensating-control recovery rule: reconcile live state, restore the intended tree without force, re-derive the candidate from the reconciled tip, rerun exact CI, and only then integrate.

## Atomicity / retry model

Repository integration is not modeled as a multi-system atomic transaction. The authoritative ref change is one Git ref mutation performed only after live-tip verification and exact-candidate CI. `force=false` prevents using the integration path as history-rewrite recovery.

If `master` moves before a future integration, the operation must stop, inspect/reconcile the new tip, re-establish the candidate, and rerun any evidence invalidated by the changed candidate. An ambiguous mutation result must be reconciled from live GitHub state before another write.

## Security and residual risk

The accepted fallback does **not** remove or conceal the hosting limitation. With the current GitHub plan, an out-of-band repository administrator remains technically able to force-push/delete the branch because the hosting provider is not enforcing those restrictions server-side.

Mitigations are process-enforced and machine-checked for the normal JARVIS implementation path: exact candidate CI, temporary branches, stale-tip rejection, non-force ref updates, post-integration verification, and a mandatory transition to server-enforced mode when the capability becomes available.

This residual risk is the reason Security and Enterprise Hardening are scored 8 rather than 9 or 10.
