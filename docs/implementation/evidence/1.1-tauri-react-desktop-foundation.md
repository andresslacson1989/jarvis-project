## Windows-native qualification repair

The original 1.1 implementation incorrectly inherited Ubuntu as a Tauri host qualification surface from the Phase 0 CI runner. The repaired workflow preserves the existing mandatory CI context but runs both mandatory jobs on `windows-2025`.

`windows-tauri-build` now proves on native Windows:

- literal PR-head checkout;
- exact checkout SHA verification;
- pinned Node/pnpm/Rust toolchains;
- clean checkout Rust formatting;
- `cargo check --locked --workspace --target x86_64-pc-windows-msvc`;
- `cargo check --locked -p jarvis-desktop --target x86_64-pc-windows-msvc`.

`static-ci` depends on that native Windows prerequisite and fails closed unless it succeeds. The inherited Phase 0/static/security/dependency/provenance/architecture/test gates all remain mandatory on Windows.

The Linux Tauri host prerequisite installation (`libwebkit2gtk-4.1-dev`, `libxdo-dev`, `libayatana-appindicator3-dev`, `librsvg2-dev`, and related Ubuntu host setup) was removed from active qualification and is regression-prohibited by the desktop foundation checker.

## Tauri context-generation root cause and repair

The prior Windows build consumed `tauri::tauri_build_context!()`, which expects a generated `OUT_DIR/tauri-build-context.rs`, while the crate used the standard `tauri_build::build()` hook without configuring build-time context codegen. Native Windows qualification therefore failed because the included context file did not exist.

The host now uses `tauri::generate_context!()` with the existing `tauri_build::build()` build hook. The exact pinned native Windows workspace and desktop Tauri builds both pass on the implementation candidate.

## Windows resource gate

`apps/desktop/src-tauri/icons/icon.ico` is present as a build-only Windows resource required by the current Tauri build path. The foundation checker validates ICO structure fail-closed, and deterministic tests cover missing, valid, and malformed resource cases.

This resource is not claimed as the canonical JARVIS production brand asset. Canonical brand sources and generated production icon variants remain owned by Section 1.11 / later packaging qualification.

## Clean-checkout and deterministic test-harness repair

A repository-owned `.gitattributes` policy establishes LF text checkout while keeping ICO and other image assets binary. The prior CI workaround that rewrote tracked Rust files after checkout was removed and is regression-prohibited.

Moving the full mandatory path to Windows exposed a platform bug in the normal test harness: a Windows absolute path was passed directly to Node's `--import` option. The runner now converts only the preload module path to a `file:` URL with `pathToFileURL(...).href`; test-file arguments remain ordinary filesystem paths. Regression tests verify the portable argument shape and qualification-profile behavior.

## Exact candidate evidence binding

Pull-request workflows check out `github.event.pull_request.head.sha` and verify it with `git rev-parse HEAD`.

A separate defect was found in the evidence generator: it previously recorded `GITHUB_SHA`, which on a pull-request run refers to GitHub's PR merge ref rather than the literal source candidate. The repaired workflow passes `JARVIS_CANDIDATE_SHA` using the same PR-head expression as checkout, and the generator validates that value as an exact 40-hex SHA.


The evidence therefore binds to the literal implementation candidate rather than the synthetic PR merge commit.
