## Contract mapping

### Exact modeled identities

- `PlatformFamily = WINDOWS | LINUX | ANDROID`.
- `RuntimeRole = FULL_HOST | COMPANION`.
- Runtime role is explicit and cannot be inferred from platform family.
- `PlatformRuntimeIdentity` carries `platform`, `runtimeRole`, `architecture`, and `backendProfileId` exactly.
- `PlatformCompatibility` carries `platform`, `runtimeRoles`, optional `osVersionRange`, and optional `architecture` exactly.
- `PlatformPathRef` carries `platform` and `value` exactly.

### Qualification / support separation

The schemas and TypeScript source explicitly state that a modeled or schema-valid platform/runtime identity is **not** support or qualification evidence. Linux/Android values therefore remain modeled future identities only. Windows V1 production support still requires the exact qualified Windows 11 x64 `FULL_HOST` support tuple and later contract-defined evidence.

### Bounded fail-closed behavior

The object schemas use `additionalProperties: false`; required identity/path fields are mandatory; platform/role values are closed enums; identity strings, OS-range strings, architecture entries, arrays, and paths have explicit bounds; duplicate compatibility roles/architectures are rejected.

`PlatformCompatibility.runtimeRoles` intentionally has no `minItems`: the governing canonical shape requires the field but does not require a non-empty declaration at this foundation layer. This avoids inventing an unsupported stronger semantic rule in `0.3`; later compatibility/support admission must remain contract-accurate and qualification-aware.

## Atomicity applicability and model

Authoritative SQLite/runtime transition atomicity is not applicable. Repository changes are scoped commits on the isolated implementation branch; a failed/stale GitHub write is never reported as success.

## Idempotency / retry-safety applicability and model

Canonical paths and schema/type names are stable. Retry requires re-fetching authoritative `master`, reconciling concurrent movement, and updating the same canonical files rather than creating competing identities or schemas.

## Failure / recovery model

If `master` moves before a write, the write must stop for reconciliation. If a branch/file write is rejected as stale, it is retried only after fresh state verification. Invalid/unknown platform/runtime data is rejected by the bounded schema rather than coerced to a nominally supported value.

## Security / least-privilege requirements

- No secret, credential, native handle, process authority, filesystem authority, provider authority, or user authorization is introduced.
- Platform capability availability/support is not represented as user/action permission.
- Extra authority/support-like object fields are rejected by the closed object schemas.
- OS-native implementation types do not cross the protocol boundary.
- Future platform modeling does not weaken Windows V1 mechanisms or create support claims.

## Observability / diagnostics requirements

Exact file/blob identities, test outcomes, support-separation semantics, scope exclusions, and the next matrix pointer are durable repository evidence. Runtime capability diagnostics begin with their owning later subsections.
