## Target-resolution model

The warning-review control distinguishes advisory platform filtering from dependency target resolution.

`cargo audit --target-os windows --target-arch x86_64` remains the lockfile vulnerability/advisory scan. A separate Cargo command derives the dependency graph used for warning disposition:

```text
cargo metadata --locked --format-version 1 --all-features --filter-platform x86_64-pc-windows-msvc
```

The checker uses `resolve.nodes`, not the unfiltered package inventory. This matches Cargo's documented and implemented target-filtered resolve behavior and matches the repository's all-feature Rust qualification.

## Checked warning policy

`third_party/rustsec-advisory-review.json` records the exact warning identity, package version, expected Windows target-resolution state, disposition, and rationale.

`tools/ci/check-rustsec-advisories.mjs` fails closed when:

- cargo-audit reports any vulnerability;
- the warning JSON is malformed or contains an unknown warning kind;
- a live warning is not in the checked review;
- a checked warning disappears from the live result and becomes stale;
- duplicate or unsorted review identities appear;
- Windows target-resolution status differs from the checked review;
- an `unsound` advisory is Windows target-resolved;
- a Windows-resolved `notice` or `yanked` warning appears;
- a Windows-resolved `unmaintained` warning lacks the explicit informational-review disposition;
- a target-unresolved warning is given a target-resolved disposition.

No `--ignore`, `--no-fetch`, `--stale`, or `--no-yanked` weakening is introduced.

## Current reviewed set

The checked review originally recorded the 15 warnings observed by the completed `e082cff...` RustSec run. RustSec advisory data is live, so the checked set is maintained against the current fresh audit result; it must not retain records that the live database no longer reports.

The current fresh audit result used while reconciling this review contains 7 warnings. Eight former GTK-family records (`RUSTSEC-2024-0411`, `0412`, `0413`, `0415`, `0416`, `0418`, `0419`, and `0420`) are no longer present in the live result and were removed from the checked review. This is review-set maintenance, not an advisory ignore or a scanner weakening.

Expected Windows/x64 all-features target resolution:

- **5 target-resolved `unmaintained` warnings:** `unic-char-range`, `unic-common`, `unic-char-property`, `unic-ucd-version`, `unic-ucd-ident`;
- **2 target-unresolved warnings:** `proc-macro-error` and `glib 0.18.5` / `RUSTSEC-2024-0429` (`unsound`).

The `glib` record is not accepted as Windows-reachable risk. Its checked disposition is target-unresolved, and the deterministic checker hard-fails if Cargo ever resolves that affected package into the Windows graph.

The `proc-macro-error` record is also target-unresolved and remains checked so any future Windows target-resolution change fails closed.

The five UNIC-family records are informational `unmaintained` advisories and are currently transitive in the Windows Tauri dependency graph. Their checked acceptance is limited to that informational maintenance status; a vulnerability, unsoundness advisory, warning-kind change, package-version change, advisory-set change, or target-resolution change fails the gate.
