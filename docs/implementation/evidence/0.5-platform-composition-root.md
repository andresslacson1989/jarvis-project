### Composition behavior

- The Windows V1 backend registration identity is `WINDOWS` + `FULL_HOST` + `x64` with backend profile id `windows-v1-x64-full-host`.
- `platform/composition.ts` is the single V1 platform/runtime selector introduced by this subsection.
- Only the exact Windows V1 tuple is selectable.
- Linux `FULL_HOST`, Android `COMPANION`, Windows `COMPANION`, and Windows `arm64` requests return `UNAVAILABLE` with stable reason `PLATFORM_BACKEND_UNQUALIFIED`.
- No weaker generic fallback exists.
- All eleven concrete capability bindings are explicitly `null` in 0.5. Registration therefore cannot be misread as capability availability/qualification; later owning subsections must supply and qualify concrete native implementations.
- The Linux source namespace contains documentation only. It does not expose an executable registration, factory, or support claim.

## Atomicity / idempotency / failure model

Atomicity: **N/A**. 0.5 performs no authoritative state mutation or external consequential effect; it defines immutable registration facts and a pure deterministic selection function.

Idempotency/retry safety: repeated composition for the same request yields the same semantic result. Capability-binding creation yields the same all-unbound semantic state on every call while returning a fresh immutable container.

Failure/recovery: unsupported/unqualified platform/runtime/architecture tuples fail closed with a stable reason code. No fallback backend, Linux runtime, or weaker native mechanism is attempted.

## Scope containment

0.5 intentionally does **not** implement Win32/DPAPI/named-pipe/Job-Object/session/window/path/audio/update/UAC mechanisms. Those remain with their owning later subsections. It also does not introduce toolchains, package-manager configuration, test architecture, CI enforcement, release qualification, or Linux production runtime code.
