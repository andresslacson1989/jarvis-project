## Behavior proven

- The deterministic runtime identity is exactly `WINDOWS`, `FULL_HOST`, `x64`, profile `windows-v1-x64-full-host`.
- Target validation occurs before host selection; host selection occurs before `tauri::Builder::default()`.
- The production registration path has one static registration constructor and no mutable registration-count or collection-based selection mechanism.
- Registered selection returns one stable host projection with `CapabilityBindingsState::UnavailableUnqualified`; it does not claim native capability qualification.
- `Missing`, `Unavailable`, `Unqualified`, and `Conflicting` registration states fail closed and do not invoke the injected runner.
- Invalid platform, runtime role, architecture, and backend profile identity tuples fail closed and do not invoke the injected runner.
- Unsupported non-Windows targets and unsupported Windows architectures return explicit failure variants through compile-time target branches.
- Every startup failure maps to exit code `1` and a bounded, control-character-free diagnostic.
- A Tauri runtime failure remains a non-success result; no success status leaks after runner failure.
- Existing navigation behavior remains bounded: debug allows only `http://127.0.0.1:5173` and production allows only `http://tauri.localhost` without an explicit port. New-window requests are denied and production devtools remain disabled.

## Atomicity, idempotency, failure, and recovery model

This subsection does not mutate JARVIS durable authoritative state or perform an external consequential operation, so database atomicity is not applicable. Host selection is a pure deterministic boundary; repeated selection of the registered identity returns the same projection. Invalid identity/registration/target state fails before Tauri construction, and runner failure is returned as non-success. There is no retryable external effect or ambiguous provider mutation in this subsection; later lifecycle/process-recovery semantics remain owned by their later subsections.
