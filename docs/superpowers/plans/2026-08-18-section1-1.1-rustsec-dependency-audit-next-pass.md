## Selected mechanism

Use RustSec `cargo-audit` version `0.22.2` as an exact-pinned CI-only security tool.

Installation:

```text
cargo install cargo-audit --locked --version 0.22.2 --no-default-features
```

Audit:

```text
cargo audit --file Cargo.lock --target-os windows --target-arch x86_64
```

Rationale:

- exact `0.22.2` version pin;
- `--locked` requires cargo-audit's published lockfile dependency resolution;
- selected repository Rust `1.97.1` exceeds cargo-audit 0.22.2's declared Rust `1.88` minimum;
- binary scanning is cargo-audit's default optional feature but is not needed for this lockfile audit, so it is disabled to reduce CI security-tool dependency surface;
- explicit `--file Cargo.lock` avoids relying on implicit lockfile generation/discovery;
- `windows + x86_64` binds the scan to the current V1 production target while future Linux remains unqualified;
- the RustSec advisory database is fetched normally and stale-data mode is prohibited;
- no advisory ignore list is allowed;
- workflow GitHub token remains `contents: read`; no Checks/Issues write permission is added.

- deterministic tests for pinning, least privilege, target scope, provenance, no-ignore/no-stale behavior, and PASS-evidence binding.

## Failure policy

The first real RustSec execution is authoritative evidence for the current lockfile.

- Do not use `--ignore`, `--no-fetch`, `--stale`, or `--no-yanked` to manufacture a pass.
- Do not silently add advisory waivers.
- If cargo-audit reports a vulnerability, inspect the advisory, affected package/version/target path, and available fix before making any status claim.
- A reachable Critical/High production-path vulnerability is a hard blocker under the Operations Contract unless a narrow contract-compliant exception is explicitly approved and documented.
- Lower-severity findings are not hidden; the default no-threshold RustSec scan is intentionally stricter and may fail on them pending review rather than silently accepting them.
