## Selected mechanism

Use RustSec `cargo-audit` version `0.22.2` as an exact-pinned CI-only security tool.

Installation:

```text
cargo install cargo-audit --locked --version 0.22.2 --no-default-features
```

Audit:

```text
cargo audit --file Cargo.lock --target-os windows --target-arch x86_64
```

Rationale:

- exact `0.22.2` version pin;
- `--locked` requires cargo-audit's published lockfile dependency resolution;
- selected repository Rust `1.97.1` exceeds cargo-audit 0.22.2's declared Rust `1.88` minimum;
- binary scanning is cargo-audit's default optional feature but is not needed for this lockfile audit, so it is disabled to reduce CI security-tool dependency surface;
- explicit `--file Cargo.lock` avoids relying on implicit lockfile generation/discovery;
- `windows + x86_64` binds the scan to the current V1 production target while future Linux remains unqualified;
- the RustSec advisory database is fetched normally and stale-data mode is prohibited;
- no advisory ignore list is allowed;
- workflow GitHub token remains `contents: read`; no Checks/Issues write permission is added.

## Failure policy

The first real RustSec execution is authoritative evidence for the current lockfile.

- Do not use `--ignore`, `--no-fetch`, `--stale`, or `--no-yanked` to manufacture a pass.
- Do not silently add advisory waivers.
- If cargo-audit reports a vulnerability, inspect the advisory, affected package/version/target path, and available fix before making any status claim.
- A reachable Critical/High production-path vulnerability is a hard blocker under the Operations Contract unless a narrow contract-compliant exception is explicitly approved and documented.
- Lower-severity findings are not hidden; the default no-threshold RustSec scan is intentionally stricter and may fail on them pending review rather than silently accepting them.

## Informational-warning review next pass

The first completed exact-head RustSec execution on candidate `e082cffddb103967ea3def5c612fbe98517cbb0f`, run `32132240232`, proved that the scanner and advisory-database freshness path worked, but it also reported 15 RustSec informational warnings: 14 `unmaintained` records and one `unsound` record.

The runner again reported that blind rerun-to-green was not performed.

Primary-source verification established an important distinction:

- cargo-audit `--target-os` / `--target-arch` filter advisories by advisory platform metadata; they do not turn `Cargo.lock` into a Windows-only dependency graph;
- Cargo `metadata --filter-platform x86_64-pc-windows-msvc` filters the `resolve` graph to dependencies activated for that target;
- `--all-features` is required here to match the repository's all-feature Rust qualification;
- the `packages` array is not the target-filtered authority; `resolve.nodes` is.

The GREEN control therefore does not suppress RustSec warnings and does not blanket-deny all informational warning kinds. Instead it:

1. keeps the normal human-readable cargo-audit execution;
2. captures a second machine-readable cargo-audit JSON result;
3. derives the Windows/x64 all-features resolved dependency graph with Cargo metadata;
4. compares the exact live warning set with `third_party/rustsec-advisory-review.json`;
5. fails on any new warning, stale reviewed warning, duplicate/malformed record, unknown warning kind, or target-resolution drift;
6. hard-fails if an `unsound` advisory becomes Windows target-resolved;
7. hard-fails Windows-resolved `notice` or `yanked` informational warnings pending explicit policy work rather than silently accepting them;
8. permits only explicitly reviewed Windows-resolved `unmaintained` informational records under the checked disposition;
9. requires target-unresolved warnings to remain target-unresolved;
10. binds PASS evidence to the successful warning-review gate.

The checked review currently expects five Windows-resolved UNIC-family `unmaintained` records and ten target-unresolved GTK/glib/proc-macro records. Those counts are not self-certifying: the final exact-head CI must derive them again from the live advisory result and Cargo's filtered resolve graph. Any difference is a failure to investigate, not a reason to update the review file mechanically.

No success is claimed by this section merely because the GREEN implementation exists.
