# JARVIS Contract v1.0.2 Consolidation Design

**Date:** 2026-08-11
**Status:** Approved consolidation design
**Target branch:** `codex/contract-v1.0.2-consolidation`

## Goal

Produce one contradiction-free, implementation-ready JARVIS contract baseline that incorporates every still-valid architectural decision without requiring implementers to mentally overlay chains of superseding ADRs and stale normative documents.

The final repository must have exactly one current source of implementation truth. ADRs remain decision history and rationale, but the active contract itself must already contain the effective rules.

## Design principles

1. **One current normative baseline.** `docs/JARVIS-IMPLEMENTATION-CONTRACT-v1.0.2.md` is the sole top-level implementation contract.
2. **Normative appendices are current, not patch layers.** Runtime, protocol/schema, data/state, security, coding, verification/release, implementation plan, and release profile are rewritten to v1.0.2 semantics where needed.
3. **ADRs are history, not mandatory overlays.** Accepted ADRs explain why a rule exists. An implementer should not need to read an ADR to discover the current rule.
4. **No duplicate ADR identity in the canonical lineage.** The accepted ADR-054 through ADR-068 sequence on `codex/contract-consistency-fixes` remains the canonical numbering lineage. The divergent `codex/contract-implementation-lock` branch is treated as non-authoritative historical work; its duplicate ADR-054/055/056 identifiers are not imported as ADRs.
5. **No valid work is discarded.** Useful material from the divergent implementation-lock branch—especially the consolidated top-level contract, Release Profile, Coding Standards, discriminated ExecutionScope, recovery details, and early implementation proofs—is incorporated into v1.0.2 without carrying its colliding ADR identities.
6. **Later valid semantics are folded in directly.** ADR-057 through ADR-068 and the fresh review hardening are represented directly in current normative documents.
7. **Historical documents are visibly historical.** v0.1, v1.0, and superseded implementation references remain available for provenance but are explicitly non-normative for new implementation.
8. **No silent product-scope loss.** V1 retains mandatory Local filesystem/Git, GitHub, Codex/OpenAI, Proxmox VE, and voice requirements; SSH, Google Workspace, Microsoft 365, and Cloudflare remain mandatory for the first feature-bearing post-V1 release under ADR-067.

## Precedence and amendment model

The consolidation intentionally removes ordinary “overlay” interpretation.

For normal implementation work:

1. v1.0.2 top-level contract and normative appendices govern;
2. the active Release Profile selects the concrete supported release subset;
3. ADRs provide rationale/history only where their effective decision has already been incorporated.

For a future architecture amendment, a new ADR may temporarily establish a decision only if the same change also updates every affected normative document before implementation may rely on it. A merged ADR that leaves contradictory normative wording behind is incomplete.

This creates a **synchronous amendment rule**: accepted architecture change + reconciled canonical contract move together.

## Fresh hardening folded into v1.0.2

### Engineering-worker delegated sandbox boundary

A shell-capable software-engineering provider is not equivalent to a JARVIS typed tool. V1 will define a delegated `WORKSPACE_ENGINEERING` execution capability:

- assigned project/worktree writes only;
- project/build/test execution needed for engineering;
- network disabled by default for delegated shell execution unless a narrowly qualified provider policy explicitly enables it;
- no integration credentials by default;
- no direct deployment, push, infrastructure mutation, email/send, or other consequential external operation merely because the provider shell can technically invoke a client;
- external consequential actions return to JARVIS typed tools/integrations and PermissionEngine;
- provider-native sandbox behavior is conformance-tested rather than assumed from prompts.

Windows Job Objects remain mandatory lifecycle/resource containment but are not misrepresented as filesystem/network security isolation.

### Tauri/WebView security boundary

The privileged desktop WebView will be defined as bundled-local-content only for the authoritative UI. Production shall require:

- explicit Tauri capability allowlists per window/WebView;
- no privileged remote-origin capabilities;
- restrictive CSP enabled in production;
- no remote executable script/CDN dependency in the privileged WebView by default;
- external links opened outside the privileged WebView;
- untrusted HTML/Markdown rendered as sanitized data;
- unexpected navigation blocked;
- production devtools disabled except a separately gated diagnostic/developer mode;
- Tauri/runtime security fixes included in version qualification.

### Deterministic PermissionEngine precedence

The current policy engine will define exact decision order:

1. hard system invariant/mandatory safety rule;
2. explicit deny;
3. authenticated session/automation eligibility;
4. authority-envelope scope containment;
5. required capability/permission and locality/budget/resource constraints;
6. current explicit instruction authorization;
7. matching standing permission;
8. required approval/final confirmation;
9. allow.

Historical precedent may help interpret reversible subordinate work or suggest standing permission, but it cannot independently authorize HIGH/CRITICAL actions or waive an approval boundary. AI confidence is never an authorization input.

### Portable SQLCipher backup key handoff

ADR-062 remains valid but v1.0.2 makes the database-snapshot key path explicit. A portable backup package must contain, inside its authenticated encrypted payload, enough protected key material to open the SQLCipher backup snapshot on a clean machine. The preferred semantics are:

- live database uses a local random `DB_DEK`;
- each backup package uses an independent random backup DEK;
- the package contains the encrypted SQLite snapshot plus an authenticated backup-internal wrapping of the snapshot database key (or an explicitly equivalent re-keyed snapshot scheme);
- portable passphrase/other portable key slot unlocks the backup DEK;
- restore decrypts/authenticates the package, obtains the snapshot key, validates/opens the snapshot, then re-keys restored state with a fresh local `DB_DEK` protected by the new Windows profile;
- ordinary integration credentials remain excluded.

A portable backup is not considered verified unless clean-profile restore using only its declared portable recovery factor succeeds in qualification.

### Consequential-operation race control

Target re-resolution immediately before execution remains mandatory. Where the external system supports conditional mutation, consequential adapters must also use expected-version/ETag/ref/hash/generation or equivalent compare-and-set semantics. A precondition mismatch causes re-resolution/re-approval as required; it does not silently retry against changed state.

### Session-password recovery semantics

Session authentication and data recovery remain separate. V1 does not provide a weak “forgot password” bypass based only on access to an unlocked Windows desktop.

- If a verified portable JARVIS recovery factor exists, the user may use an explicit recovery workflow to establish a new JARVIS session password after recovery checks.
- Without an applicable recovery factor, the old session password is not recoverable from its verifier.
- Clean-machine portable restore always establishes a new session password after state decryption/validation.
- Integration credentials are not recreated from portable state backup; affected accounts become `REAUTH_REQUIRED`.

## V1 scope treatment of external modules

ADR-057 execution classes remain architectural law. V1 must implement the class model and must never run externally installed executable code in Core. However, the Release Profile need not promise an open third-party executable-module ecosystem. `EXTERNAL_MANAGED` is supported only for modules explicitly shipped/qualified by the active release/catalog; arbitrary public executable-module installation remains disabled/unqualified unless promoted by a later Release Profile.

## Verification strategy

The consolidation is complete only when a document-level consistency review confirms:

- one canonical contract version is advertised by README and AGENTS;
- no active appendix names v1.0/v1.0.1 as its normative parent;
- no active document says `RESUMING` is both durable and non-durable;
- one sensitivity/locality vocabulary is used;
- one money representation is authoritative;
- one approval descriptor/canonicalization rule is authoritative;
- one V1 integration release set is declared;
- Proxmox is consistently mandatory for V1;
- Job Objects are consistently mandatory for managed process trees;
- engineering-worker delegated shell authority is explicitly narrower than provider/native OS capability;
- Tauri capabilities/CSP/navigation rules are explicit;
- PermissionEngine precedence is deterministic;
- portable backup clean-profile database-key semantics are complete;
- no duplicate ADR identifier is introduced into the canonical branch;
- older branch artifacts are explicitly non-authoritative.

## Success condition

An engineer should be able to start with README/AGENTS, read the v1.0.2 suite, and implement JARVIS without asking: “Which later ADR supersedes this sentence?”

> **History explains the contract. The current contract defines the product. No implementer should have to reconstruct the current architecture from superseding patches.**
